## Gray fog erosion over time (change-list item 2: 灰雾侵蚀，局内时间压力)

**概要**

What exists today: SkyPrisonGrayLoss is a runtime-only component (it is not serialized in any prefab, scene or asset, so the code defaults always apply). Its API is EnsureOn(GameObject), AddLoss(float), Recover(float), Clear(), BaseMaxHealth and Ratio01. It clears itself on SceneManager.activeSceneChanged, adds SkyPrisonGrayLossScreenGrain in Awake, and starts a natural recovery of 4%/s once no AddLoss has happened for 3s. SkyPrisonGrayFurnace shows the pattern to copy: every frame it calls SkyPrisonGrayLoss.EnsureOn(SkyPrisonPlayerAuthority.CurrentPlayerUnit.gameObject).AddLoss(BaseMaxHealth/secondsToFull*dt).

The run lifecycle is AFPRuntime's static OnSessionBegan / OnSessionEnded events. BeginSession fires on sceneLoaded whenever SaveManager.Player.activeSession != null. That means it fires when LoadingScene loads, before the raid scene exists. In the editor it also fires automatically for scenes whose path contains /Maps/Raid/. EndSession is called by ExtractionTerminal.ExtractRoutine and by DeathSettlementUI.OnConfirm. Pause menu 'return to main menu' does not call it.

Proposal: add a new cross-scene runtime singleton, SkyPrisonGrayFogErosion, created in GameBootstrap next to AFPRuntime. It resets its clock on OnSessionBegan and stops on OnSessionEnded. The clock only ticks with scaled time, while not loading, in a /Maps/Raid/ scene, with a live player. It computes the phases Safe (<60%), Warning (60–70%) and Erosion (>70%) of a configurable expected run length (900s; night ×0.8). In Erosion it feeds gray loss through the existing SkyPrisonGrayLoss API at a ramping rate. Within extractionSafeRadius of any ExtractionTerminal (found through InteractableRegistry.All) it stops adding gray. The warning look is a runtime URP Volume (priority 101, desaturate + gray color filter + vignette), built the same way as the existing grain Volume. Warning and erosion start each play a sound that already has clips (BannerSignal, BannerFlash). A separate self-bootstrapping HUD component, SkyPrisonGrayFogHUD, built at runtime like SkyPrisonAFPHUD, shows only the phase icon and label, with no countdown.

Code changes outside the two new files are small and additive:
- one method in SkyPrisonGrayLoss (HoldNaturalRecovery);
- 3 lines in GameBootstrap;
- optional: a dev hotkey, and a one-line fog-of-war tint hook.
No prefab, scene or asset edits are needed, and ExtractionTerminal.cs is not touched (item 3 owns it).

3. 3) SkyPrisonGrayFogErosion: [SerializeField] config with defaults. Create it only from code, so these are the effective values and there is nothing in prefabs or scenes to check.

- [Header("夜版")] `nightTimeScale = 0.8f` (all phase times ×0.8 → 12 min), `nightErosionRateMultiplier = 1.25f`
- [Header("撤离终端安全区")] `extractionSafeRadius = 10f`, `showSafeZoneRing = true`, `ringColor = new Color(0.4f,1f,0.7f,0.45f)` (same green as the minimap extraction icon), `ringWidth = 0.18f`

With these defaults, a player who never enters a safe zone reaches about 67% gray at 15:00 and dies about 16:15 (day). At night the figures are about 12:00 and 13:00. Both fall inside the doc's 12–18 / 10–15 min targets. Mark all values 需实测.
4. 4) SkyPrisonGrayFogErosion lifecycle. Copy the AFPRuntime singleton pattern.
- Awake: `if (Instance != null && Instance != this) { Destroy(gameObject); return; } Instance = this;` then BuildVolume().
- OnEnable: `AFPRuntime.OnSessionBegan += HandleSessionBegan; AFPRuntime.OnSessionEnded += HandleSessionEnded; SceneManager.activeSceneChanged += HandleSceneChanged;`
- OnDisable: unsubscribe all three.
- Start: `if (AFPRuntime.Instance != null && AFPRuntime.Instance.IsInSession) HandleSessionBegan();` (defensive).
- HandleSessionBegan: `_running = true; _elapsed = 0; _pendingLoss = 0; _night = SkyPrisonRaidRunContext.Night; SetPhase(Phase.Safe);`
- HandleSessionEnded: `_running = false; SetPhase(Phase.None); ApplyVisuals(0f);`
- HandleSceneChanged: clear the ring dictionary; the rings belong to the old scene and are destroyed with it.
- OnDestroy: Destroy the runtime VolumeProfile, the same as the grain component.
5. 5) SkyPrisonGrayFogErosion.Update eligibility gate. All of these must hold:
`_running && AFPRuntime.Instance != null && AFPRuntime.Instance.IsInSession && !SceneLoader.IsLoading && IsRaidScene() && SkyPrisonPlayerAuthority.CurrentPlayerUnit != null`
- IsRaidScene: `SceneManager.GetActiveScene().path.Contains("/Maps/Raid/")` cached per scene.handle. This is the same rule as AFPRuntime.TryEditorAutoSession and the same caching as SkyPrisonHubCombatGate.IsHubScene. It excludes LoadingScene, MainMenu, the hubs and /Maps/Final/Tower.
- If not eligible: `IsActive=false; ApplyVisuals(0f); return;` This makes the volume disappear in the main menu after a pause-menu exit while IsInSession is still true.
- Resolve health with `unit.GetComponentInChildren<UnitHealthController>(true)`, cached per unit.
- If `!health.IsDead`, do `_elapsed += Time.deltaTime`. Use scaled time: it stops for pause and loading (timeScale=0) and while the player is dead or waiting for the revive choice.
6. 6) SkyPrisonGrayFogErosion phase and erosion math (s = _night ? nightTimeScale : 1):
- `float T = expectedRunSeconds*s, tSafe = T*safeEndFraction, tErode = T*erosionStartFraction;`
- Phase = `_elapsed < tSafe ? Safe : _elapsed < tErode ? Warning : Erosion`; `WarningProgress01 = Mathf.InverseLerp(tSafe, tErode, _elapsed)`.
- On a phase change: `SetPhase` invokes OnPhaseChanged. It plays `SkyPrisonSystemSEPlayer.Play(SkyPrisonSystemSEType.BannerSignal)` on entering Warning and `SkyPrisonSystemSEPlayer.Play(SkyPrisonSystemSEType.BannerFlash)` on entering Erosion. Do not use Notice, which has no clip.
- `PlayerInSafeZone = IsInExtractionSafeZone(unit.transform.position)`.
- In Erosion, when the player is alive:
  - `var gray = SkyPrisonGrayLoss.EnsureOn(unit.gameObject);`
  - `if (suppressNaturalRecoveryDuringErosion) gray.HoldNaturalRecovery();`
  - `if (!PlayerInSafeZone) { float rate = Mathf.Min(erosionMaxRatePerSecond, erosionStartRatePerSecond + (erosionRateAtExpectedEnd - erosionStartRatePerSecond) * Mathf.Max(0f, _elapsed - tErode) / Mathf.Max(1f, T - tErode)) * (_night ? nightErosionRateMultiplier : 1f); _pendingLoss += gray.BaseMaxHealth * rate * Time.deltaTime; if (_pendingLoss >= 0.5f) { gray.AddLoss(_pendingLoss); _pendingLoss = 0f; } }`
  - Accumulating like this follows SkyPrisonGrayLoss's own _recoverAccumulator idea and avoids rebuilding the stat modifier every frame. HoldNaturalRecovery keeps recovery off between the chunks.
- Revive fix: track `_wasDead`. On a dead→alive transition while Phase==Erosion, call `gray.Recover(gray.BaseMaxHealth * reviveGrayRecoverFraction)`. Without it, a revive after a gray death leaves `_loss` near BaseMaxHealth, and the next AddLoss kills again once `_reviveImmunityExpiry` ends.

**风险**

- OnSessionBegan fires while LoadingScene is active, before the raid scene exists. Without the `!SceneLoader.IsLoading && path.Contains("/Maps/Raid/")` gate the clock would tick during loading, or in the hub after a dev F5 BeginSession.
- Pause-menu 'return to main menu' never calls EndSession, so IsInSession stays true in MainMenu. The volume weight must be forced to 0 whenever the component is not eligible. If the player continues the save afterwards, AFPRuntime will not BeginSession again, so the clock resumes from where it was. A fresh load with activeSession resets it. Either behaviour is acceptable but differs.
- SkyPrisonRaidRunContext.Night is static and not saved. A night run resumed after a game restart is treated as day.
- SkyPrisonGrayLoss clears on every activeSceneChanged, so an in-raid SceneLoader.SwitchMap wipes the gray while the erosion clock keeps going. This is existing behaviour and not changed by this plan.
- SkyPrisonBrightnessManager's global Volume (priority 100, ColorAdjustments with every parameter overridden) wins over any lower-priority ColorAdjustments. The new volume must use priority 101 and must not override postExposure, or it would break the brightness setting.
- Natural gray recovery is 4%/s after 3s. Without HoldNaturalRecovery, standing in an extraction safe zone would fully clear the gray in 25s and undermine the 'greed vs leave' pillar. HoldNaturalRecovery also suppresses recovery from furnace gray during erosion, which is intended.
- Revive after a gray-caused death: the loss stays near BaseMaxHealth and the player dies again once revive immunity ends. reviveGrayRecoverFraction (0.5) avoids this. This is a design choice the user and the item-5 owner should confirm.
- No committed scene or prefab contains an ExtractionTerminal (only the editor whitebox builder adds them). The safe zone and rings will do nothing until terminals are placed, so erosion is untestable near terminals right now.
- Calling AddLoss every frame would allocate a List/StatModifier and recalculate stats each frame for minutes. The 0.5 HP accumulator avoids this; keep it.
- The default numbers have not been tested. A player who never reaches a safe zone or medical station dies at about 16:15 (day) or 13:00 (night). The doc says to measure the real run length first; tune expectedRunSeconds.
- The /Maps/Raid/ rule excludes /Maps/Final/Tower. Confirm whether the final map should have erosion.
- Scaled Time.deltaTime means hit-stop or slow-motion slightly slows the clock, and pause or loading stops it (intended). Inventory and other non-pausing windows do not stop it (intended pressure).
- HUD placement (top-right of HudInstance) and the Volume's look cannot be checked visually without the editor. Anything else anchored there in other layouts could overlap.
- Merge conflicts: GameBootstrap.cs and SkyPrisonDevHotkeys.cs may also be edited by other areas' implementers; the changes are a few lines, and the self-bootstrap alternative avoids GameBootstrap.
- New .cs files need .meta files. Hand-write them with a fresh random GUID or let Unity generate them. No asset references them, so there is no GUID-stability risk.
- TMP font ZhouFangRiMingTi-2 SDF is Dynamic, so new glyphs work, but the editor prebake tool (SkyPrisonFontCharacterPrebake) will not have baked the new label strings until it is re-run. Runtime atlas growth is harmless.

**需要 Unity 编辑器的部分**

## Combat numbers rescale (change-list item 1 + item 17 size part)

**概要**

Enemy max HP comes only from each UD_*.asset `parameterValues[maxHp]`, through this path: UnitStatusRuntimeBootstrap.EnsureStatusControllerInitialization -> UnitBattleStatRuntime.EnsureInitialized(UnitDefinition) -> RebuildAll() -> ApplyDerivedResources() -> UnitHealthController.SetMaxHealthFromStatus(float). All enemy prefabs keep the health controller default of 100, and no scene or prefab overrides any of these fields. The one runtime override is SkyPrisonGuardianShield, which calls `_health.SetMaxHealth(guardianMaxHealth,false)`; its prefab has guardianMaxHealth 2000, so that value must be changed to match. Gray Furnace regen and Shatterer leg HP are both fractions of MaxHealth, so they scale on their own. Shatterer legs go from 1260 to 420 each with no edit. The furnace regen used at runtime is the prefab value 0.015, not the code value 0.025 that the change-list quotes. Two other change-list facts are also wrong: the gun's magazineSize in the asset is 120 (not 12), and the gun's negative-crit stat has no effect (130% gets clamped to x1.0). For gun damage, the plan is to raise SK_GunAttack2 `damageMultiplier` from 1 to 3 (atk 14 x 3 = 42 per shot without crit, about 48 average with crit). This is better than raising item atk because drones and anomaly burst also read `atk`. The rescale breaks two HP-relative thresholds that are tuned against absolute damage: Mirage retreatDamageRatio (one shot would make it retreat) and AfpPhysicalMastery.LargeEnemyMaxHp=300 (every enemy would count as 'large'). Both get small fixes. All spineVisualScale and model3DVisualScale values are 1, and every enemy uses the same HomingOne placeholder skeleton, so scaling by threat tier is a data-only change. The body capsule and hurtbox recalibrate from the visual bounds; melee attack hitboxes may not.

## AFP from loot boxes (change-list item 4)

**概要**

Loot boxes are not containers. Each box is a destructible unit: the UnitDefinition UD_SceneProp_NoBlood ("物资箱A", defineType=Destructible, maxHp 1, one dropProfile). SkyPrisonLootDirector spawns these boxes at SkyPrisonLootPoint spots using the counts in Resources/MapLootRegistry.asset. Only Old Factory has an entry: 85 boxes by day and 121 by night, picked from 144 points. "Opening" a box means the player breaks it. Hit → UnitHealthController → UnitDeathController.Kill(), which runs only once because it returns early unless the state is Alive. Kill() fires OnDeathStarted, which spawns the drops and the crate debris, and then the static OnAnyEnemyDied. AFPRuntime already listens to OnAnyEnemyDied. It gives 0 for boxes only because GetAFPYield lets through only Enemy, Elite and Boss identities. UnitCombatHitbox.AreHostile already makes Destructible and Item units breakable only by the Player, so this event already means "the player opened this box, for the first time". Proposed change: add a new field `lootAfpYield` to UnitDefinition (default 0, set to 100 on the box asset). Add one branch in AFPRuntime.GetAFPYield that returns lootAfpYield for Destructible/Item units. Box AFP then gets the same afpGainRate perk multiplier as kills (the perk text says "combat and scavenging"). The existing SkyPrisonAFPHUD "+N" popup and green pulse already fire on every AddAFP, so no new UI is needed. Optionally, count kill AFP and box AFP separately per run so playtests can check the 1/3 ratio.

**风险**

- There is no compiler, so keep the edits tiny. `UnitDefineType` and `UnitDefinition` are global-namespace types already used in AFPRuntime's file scope (CharacterIdentity is used there), so no new `using` is needed. `[Min(0)]` on an int is already used in MapLootRegistry.cs.
- UD_SceneProp_NoBlood is the shared 'minimal' definition for every breakable prop made with SkyPrisonBreakableCratePrefabCreator. Any decorative breakable bound to it later would also give 100 AFP. Today only loot-director boxes use it (0 placed instances in scenes). When item 14 adds high-value boxes or decorative breakables, they need their own UnitDefinition assets with their own lootAfpYield.
- The kill-AFP budget per run is unknown: Old Factory has no enemies placed in the repo, so the value 100 is a reasoned starting point, not a measured one. Use the step 4 session log in playtests to tune it toward box ≈ 1/3.
- Hand-editing .asset YAML: Unity matches keys by name, so the insert is safe if indentation is 2 spaces. Unity will re-serialize the file (adding afpYield: 50 and lootAfpYield) the next time it is saved in the editor, which causes harmless diff noise.
- Including UnitDefineType.Item in the branch: no Item-type UnitDefinitions exist today and the default is 0, so there is no effect now. It mirrors IsPlayerOnlyDestructibleTarget.
- afpGainRate now also multiplies box AFP (up to +24%). This fits the perk text but slightly raises total AFP for invested players.
- The '+N' HUD popup fires per box. Breaking many boxes in a row is noisy but already bounded by the 3-slot rotation.
- AddAFP is ignored outside a session. In the editor, a session starts automatically only for scenes under /Maps/Raid/, so testing in other scenes shows no AFP.
- Pre-existing: box breaks count as kills (SessionStatsTracker.KillCount, quest kill_any). This is unchanged unless optional step 8 is applied.

**需要 Unity 编辑器的部分**

- Playtest checks in Play mode: break a box and confirm the HUD shows '+100' and that CurrentAFP rises once per box. This cannot be confirmed without the editor.
- Optional workspace row (step 7) only needs a visual check in the SkyPrison unit-definition workspace.
- A world-space '+AFP' popup at the box position is NOT recommended without the editor. The camera sits about 200 units away with a 30° FOV, so world text size and placement need in-editor tuning. The existing HUD popup is the code-only alternative.
- Future per-type box values (item 14) need new UnitDefinition assets, ideally made by duplicating in the editor to get fresh GUIDs. Hand-making .asset/.meta files with new GUIDs is possible but riskier.

**风险**

- 关于“退出→继续游戏”：如果不做步骤 6，局中存档后退出再继续时，AFPRuntime.OnSceneLoaded 会再次触发 BeginSession → OnSessionBegan，复活标记被清掉。AFP 升级在同样的情况下也会被清零，属于已有行为。
- Unity 的 JsonUtility 不支持把自定义 [Serializable] 类的字段存成 null，读档后 Player.activeSession 很可能是一个空的非 null 实例。所以不能用 activeSession != null 判断“正在局内”，这正是本方案以 AFP 会话事件为主要重置手段的原因。BeginChapter 每局都会新建实例，所以 reviveUsed 仍然会被正确清零。
- 据点里也能打架（SkyPrisonHubCombatGate），在据点死亡同样会走 DeclineReviveAndDie。背包清空本来就在这里无条件执行，按方案耐久惩罚也会在据点死亡时生效。如果不想这样，可以给 ApplyDeathDurabilityPenalty 加条件 `AFPRuntime.Instance != null && AFPRuntime.Instance.IsInSession`（编辑器直接进 RAID 也会自动开 AFP 会话，所以这个条件在编辑器里同样成立）。
- 惩罚和背包清空走同一条存档路径：只有在 DeathSettlementUI.OnConfirm → 场景加载 → SaveManager.Save(false) 之后才会落盘。如果玩家在结算界面强制退出，背包和耐久都会回到上一次存档的状态，这是已有行为，没有变化。
- TriggerActionExecutor.cs 第 440 行会直接调用 death.Kill()，绕过 HP 归零的死亡判定。如果某个触发器用这种方式杀死玩家，就不会弹复活窗口、不会扣耐久，也不会进入死亡结算（已有问题，不在本次范围内）。
- 这里没有动 Wear() 的腐蚀倍率（×3，最少 +1）。如果有人用 Wear(entry, amount) 来实现死亡惩罚，处于腐蚀状态时死亡会让 40% 变成 120%，装备直接报废。所以惩罚必须使用新加的 ApplyMaxRatioLoss。
- ID_NewItem.asset 的描述是双引号 YAML 字符串，里面是 \uXXXX 转义，日文那段还是折行写法。手改 YAML 时容易破坏转义或引号，导致资产无法读取。改 2 秒只需要替换一个数字字符；新增句子最好在编辑器的物品检视面板里输入（SkyPrisonItemDefinitionInspectorPanel）。
- PlayerReviveProtection 用 Time.deltaTime（受 timeScale 影响）计时，而 _reviveImmunityExpiry 用 realtimeSinceStartup。时长缩到 2 秒后，如果复活时正好在顿帧或慢动作中，这两个窗口会有轻微错位，影响不大。
- GCD（s_ReviveSharedGCDExpiry、60 秒）在每局一次的规则下基本用不上了，但仍会显示在复活弹窗里，暂时保留以免改动 UI。

## Healing consumables use time / channel (change-list item 6: 回复道具要有读条)

**概要**

Healing is currently INSTANT and nothing can interrupt it. There are exactly two entry points: QuickSlotUseController.TryUseSlot (keys 1-4) and SkyPrisonInventoryInteraction.UseItem (the backpack "使用" menu). Both run the same steps in a single frame: block check, cooldown check, ItemCooldownTracker.StartCooldown, ItemEffectExecutor.Execute, then DiscardSlot. ItemDefinition has no use-time, cast-time or interrupt field. First aid has `cooldown: 2`, but that is a lockout after use, not a cast, even though its description already promises "完成恢复需要2s释放时间". The data is also inconsistent. Only 急救药物 heals at all (+30% HP). 罐头 and 冷却药剂 are marked usable but have empty `effects`, so using them just deletes them. 压缩饼干 is a Material (category 1, usability 0) and cannot be used. No item-use animation exists. The proposed change is a new runtime singleton, ItemUseChannelRuntime, created in GameBootstrap the same way as QuickSlotUseController. It is driven by a new data field `ItemDefinition.useDurationSeconds` (0 = instant, which keeps old behaviour). While channelling, the player moves at 50% speed through a UnitBattleStatRuntime external modifier on "moveSpeedRate". The channel is cancelled by UnitHealthController.OnDamaged (DoT ticks are filtered out using UnitStatusController.DotDamageApplied), by any UnitActionController state other than Normal (attack, dodge, jump, reload, hit stun, death), and by death or the near-death choice. On completion it runs the existing cooldown/Execute/Discard steps. A cancelled channel does nothing and consumes nothing. Progress is shown on a small runtime-built UGUI bar, using the same pattern as SkyPrisonBossHealthBar, so no prefab work is needed. Data: first aid gets 2 s (matching its existing text) and canned food gets 3 s plus a real HP effect. One pitfall must be handled: the player's unit definition has no `moveSpeedRate` base value, so a Multiply modifier alone would set speed to 0 and freeze the player.

**风险**

- No compiler is available. Every API used above was verified by reading the source, but typos are still possible: nested enum `UnitActionController.UnitActionState.Normal`, event signatures `Action<UnitHealthController,float>` and `Action<RuntimeStatusEntry,float>`, and `StatModifier(string,float,StatModifierOp)`.
- Missing player moveSpeedRate base: if both the code guard (step 4) and the data fix (step 16) were skipped, the Multiply modifier would freeze the player during every heal.
- DoT filtering depends on DotDamageApplied following OnDamaged synchronously. If a DoT tick is blocked (revive protection, so no OnDamaged) and a real hit lands in the same frame, the hit can be cancelled out. This is a negligible edge case. Gray-fog erosion never interrupts because it lowers maxHp instead of dealing damage.
- Every UnitActionController state other than Normal cancels the channel. That includes Jump and Reload, which makes healing stricter. If design wants jumping allowed, whitelist `UnitActionState.Jump`.
- Hits that deal 0 HP (shield absorb via IIncomingHitModifier, revive protection) do not fire OnDamaged. They interrupt only if they cause HitStun.
- The inventory may be sorted or merged mid-channel. The plan re-finds the slot by entry reference and then by definition. If the item is gone at completion, nothing happens.
- Hand-editing ScriptableObject YAML (canned food effects list, player parameterValues) must keep exact 2-space indentation. Verify the assets reimport cleanly in the editor.
- The editor tool SkyPrisonStandardItemSeeder.ApplySeed overwrites `cooldown` but not the new field, which is harmless. Re-running it would not reset useDurationSeconds.
- The runtime bar is a separate overlay canvas. It does not follow SkyPrisonHUDCombatVisibilityController fades and may need `SceneLoader.RegisterGameCanvasForReveal` if it should hide during the loading reveal. It is only visible while channelling, so this risk is low.
- Canned food can now be put in a quick slot (category Consumable) even though `canPutInQuickSlot` is 0, because that flag is ignored at runtime. This is existing behaviour, not new.
- The localized descriptions for other languages (ja-JP, en-US) of first aid and canned food do not mention use time. This is cosmetic.

**需要 Unity 编辑器的部分**

- Play-testing durations, the 50% slow, and how the interrupt feels against each enemy's hit and stun data. This cannot be judged without running the game.
- A Spine 'use item / drink' animation does not exist, and creating one needs art and the editor. Code-only alternative: the progress bar plus the existing useVFX/useSE, which Execute already plays at completion, and an optional Confirm SE at start.
- Checking the final on-screen position and size of the runtime-built progress bar against the HUD layout (and the optional quick-slot fill reuse) at different resolutions.
- Confirming in the editor that the hand-edited YAML (ID_first_aid_medicine, ID_canned_food effects entry, UD_Player_Axia_01 parameterValues) imports without errors and shows correctly in the custom SkyPrison item and unit editors.
